## 问题

报表直接查业务库：白天一跑复杂报表，业务系统就变慢；不同部门各自写 SQL，同一个指标算出不同的数。

## 适用场景

- 适合：报表直接查业务库导致变慢、各部门指标口径不一的公司
- 不值得：数据量很小、报表很少的
- 前提：业务表有更新时间字段，能做增量抽取

## 工具选型

| 方案                       | 特点                   | 适用                                 |
| -------------------------- | ---------------------- | ------------------------------------ |
| Python + pandas            | 灵活，小数据量         | ✅ 方案采用                          |
| DataX                      | 阿里开源，异构数据同步 | 国内常用                             |
| Airflow / DolphinScheduler | 任务编排               | Airflow 外企 / DolphinScheduler 国内 |
| dbt                        | SQL 建模、测试、文档   | 外企数据团队                         |

小数据量用 Python 足够；任务多了用 Airflow 编排依赖和重试。

## 怎么做

- 每天凌晨按「更新时间」增量抽取前一天变化的数据（数据量小用 Python，大的用 DataX 等工具）
- 统一口径计算指标（销售额是否含退款、门店如何归属），写入报表库（MySQL 或 ClickHouse）
- 任务之间有依赖关系的用 Airflow 编排，失败自动重试并告警
- 跑完做数据校验：行数、金额合计和业务库对账，差异超过阈值就不发布当天的报表

## 实施步骤

| 步骤 | 做什么                 | 怎么验证               |
| ---- | ---------------------- | ---------------------- |
| 1    | 确定指标口径并写成文档 | 业务方确认             |
| 2    | 按更新时间增量抽取     | 重复运行不会重复写入   |
| 3    | 汇总写入报表库         | 报表库里有前一天的数据 |
| 4    | 运行后对账校验         | 金额合计和业务库一致   |
| 5    | 失败重试并告警         | 模拟失败时收到告警     |

## 常见坑

- **增量漏数据**：业务更新数据时没改更新时间字段。确认更新时间字段可靠，或者用 binlog 同步。
- **重跑导致重复数据**：写入用追加。按日期先删后写，或用 upsert。
- **跑批时间越来越长**：数据量增长。只处理增量；大表分区。

## AI 视角

**✨ AI 能增强**

- **AI 能做什么**：用自然语言描述需求生成 SQL；解读数据异常
- **不该交给 AI**：指标口径和计算必须确定、可测试
- **怎么落地**：AI 生成 SQL 初稿，人审核并写测试

## 面试怎么讲

30 秒讲法（方案思路；没有实际落地，面试时如实说明是设计过的方案）：

> 我会每天凌晨按更新时间从业务库增量抽取前一天的数据，按统一口径汇总写入报表库。任务用 Airflow 编排，失败自动重试并告警；跑完做对账，金额合计和业务库不一致就不发布当天报表。这样白天报表不再拖慢业务系统，全公司用同一套指标。

常见追问：

**问：ETL 和 ELT 有什么区别？**

答：ETL 先转换再加载；ELT 先把原始数据加载到数仓再用 SQL 转换，适合计算能力强的数仓。

**问：如何保证跑批可重复执行？**

答：按分区（日期）先删后写，或者用 upsert，重跑结果一致。

**问：增量抽取有哪些方式？**

答：按更新时间戳、按自增 ID、基于 binlog 的 CDC（Canal、Debezium）。

**被问到「能不能用 AI」时：** AI 能写 SQL 初稿，但口径必须人确定并有测试。
