## 问题

固定阈值告警有两个盲区：

- **业务指标**：服务器、接口都正常，但支付渠道出问题导致支付成功率掉了一半，技术监控完全没告警，几个小时后财务对账才发现。业务量白天和凌晨差几十倍，固定阈值要么误报要么漏报
- **日志**：日志告警只能匹配写好的关键字。新上线的代码打出一种以前没见过的报错，没人写过规则，就一直没人知道

## 适用场景

- 适合：有线上交易、业务指标直接关系收入的公司；服务多、日志量大，人看不过来的团队
- 不值得：业务量很小、波动很大的早期产品；日志量小到人每天能看完的
- 前提：业务指标能实时采集（埋点或数据库查询）；日志已集中收集（Loki、ELK）

## 工具选型

| 方案                          | 特点                       | 适用        |
| ----------------------------- | -------------------------- | ----------- |
| Prometheus offset 同期对比    | 简单可解释，覆盖周期性波动 | ✅ 起步     |
| Prophet 等时间序列模型        | 学习日、周、节假日季节性   | ✅ 方案采用 |
| Drain 日志模板聚类            | 把日志归成模板，发现新模板 | ✅ 方案采用 |
| Grafana ML / Datadog Watchdog | 托管的异常检测             | 外企常用    |
| 阿里云、腾讯云智能告警        | 云上托管                   | 国内云上    |

先用同期对比打底，复杂指标再用模型；日志用模板聚类，比关键字规则多发现「没想到的错误」。

## 怎么做

**指标：动态基线**

- 把核心业务指标纳入监控：每分钟订单数、支付成功率、注册数、登录失败率；系统指标挑接口延迟、错误率
- 简单指标先用同期基线（和上周同一时刻比），偏离超过 40% 并持续 10 分钟才告警
- 季节性复杂的指标（节假日、大促）用 Prophet 每天离线训练，预测下一天每分钟的正常区间，实际值连续跑出区间就告警
- 凌晨量太小时不判断，避免分母太小造成误报

**日志：新模式发现**

- 每 5 分钟从 Loki 拉取 ERROR / WARN 日志，用 Drain 算法把日志归成模板（变量部分如 ID、IP 替换成 `<*>`）
- 和过去 7 天的模板库比：出现新模板、或者某个模板数量突增 10 倍，就告警
- 告警附上样例日志、首次出现时间、最近一次发布，方便判断是不是新代码引起的

## 实施步骤

| 步骤 | 做什么                                 | 怎么验证                   |
| ---- | -------------------------------------- | -------------------------- |
| 1    | 和业务确定核心指标，应用埋点暴露指标   | Prometheus 能采集          |
| 2    | 编写同期对比告警规则                   | 历史数据回放时能触发       |
| 3    | 复杂指标训练 Prophet，输出正常区间     | 回放过去的故障能检测出来   |

| 6    | 节假日、大促前调整，每周看误报并调参   | 误报率逐周下降             |

## 关键代码

示例代码（简化），没有在生产环境运行。业务指标同期对比：

```promql
# 当前订单速率比上周同期低 40% 以上，且上周同期有一定量
(
  sum(rate(orders_created_total[10m]))
    / sum(rate(orders_created_total[10m] offset 1w))
) < 0.6
and sum(rate(orders_created_total[10m] offset 1w)) > 0.1
```

日志新模板发现（Drain3）：

```python
from drain3 import TemplateMiner
from drain3.file_persistence import FilePersistence

miner = TemplateMiner(persistence_handler=FilePersistence("templates.bin"))
for line in loki.query('{level="error"}', since="5m"):
    r = miner.add_log_message(line)
    if r["change_type"] == "cluster_created":  # 7 天模板库里没有
        alert(f"新报错模式：{r['template_mined']}", sample=line, deploy=recent_deploy())
```

## 效果指标

| 指标               | 做之前           | 预期效果（估算）    |
| ------------------ | ---------------- | ------------------- |
| 业务异常发现       | 几小时到第二天   | 十几分钟            |
| 技术正常但业务异常 | 发现不了         | 能发现              |
| 没写规则的新报错   | 用户反馈后才知道 | 首次出现 5 分钟内   |
| 误报               | 固定阈值误报多   | 动态基线 + 持续时间 |

业务异常在几十分钟内被发现，而不是第二天对账时；新代码引入的错误在发布后几分钟就有人知道。

## 常见坑

- **节假日、大促误报**：和上周同期不可比。模型里加入节假日日历，大促前临时调整。
- **凌晨量太小比例波动大**：分母太小。加最小量条件。
- **指标采集本身中断被当成业务下跌**：埋点或采集故障。区分「没数据」和「数据为 0」，采集中断单独告警。
- **日志模板太碎**：变量没识别出来，每条都成了新模板。预先用正则把 ID、时间、IP 替换掉，并调整相似度阈值。
- **模型说不清为什么告警**：业务方不信任。告警里附上预测区间和实际曲线，让人一眼看出偏离。

## AI 视角

**🤖 AI 是核心**

- **AI 能做什么**：这里的 AI 是机器学习，不是大模型——时间序列模型学习指标的正常规律，聚类算法把海量日志归成模板，找出人写不出规则的异常
- **不该交给 AI**：是否通知人、通知谁仍按告警规则；结论要能用曲线和样例日志解释
- **怎么落地**：先用同期对比打底，复杂指标再用模型；告警后可以把异常交给大模型做根因分析（见「告警根因分析」）

## 面试怎么讲

30 秒讲法（方案思路；没有实际落地，面试时如实说明是设计过的方案）：

> 我会把异常检测分成指标和日志两部分。指标方面，订单数、支付成功率这类业务指标不用固定阈值，先用和上周同期对比，复杂的再用 Prophet 学习季节性，实际值持续跑出预测区间才告警。日志方面，用 Drain 把错误日志归成模板，和过去 7 天比，出现新模板或某个模板突增就告警，并附上样例日志和最近一次发布。这能发现技术监控发现不了的业务异常和没写过规则的新报错。

常见追问：

**问：为什么业务指标不用固定阈值？**

答：业务量随时间周期变化，白天和凌晨差几十倍，固定阈值要么误报要么漏报。

**问：offset 是什么？**

答：PromQL 里取过去某个时间点的数据，比如 offset 1w 取一周前同一时刻。

**问：日志聚类有什么用？**

答：几百万行日志其实只有几百种模板。按模板统计，就能看出哪种错误是新出现的、哪种突然变多，不用事先写关键字规则。

**问：这算 AI 吗？和大模型有什么关系？**

答：属于传统机器学习，算力要求低、结果可解释，适合实时检测；大模型更适合检测之后的分析和总结，两者配合。

**被问到「能不能用 AI」时：** 异常检测本身就是机器学习；我会先用简单的同期对比，确实需要时再上模型，告警必须能解释。
