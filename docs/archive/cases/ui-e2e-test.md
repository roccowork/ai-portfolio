## 问题

每次发布前测试人员手工点一遍核心流程，费时而且容易漏；前端改动经常把别处的页面改坏，上线后才发现。

## 适用场景

- 适合：有 Web 前端、发布频繁的产品
- 不值得：界面每周大改的早期原型——测试维护成本太高
- 前提：有可重复使用的测试环境和测试账号

## 工具选型

| 方案       | 特点                           | 适用         |
| ---------- | ------------------------------ | ------------ |
| Playwright | 多浏览器、自动等待、trace 调试 | 国内外都常用 |
| Cypress    | 前端开发者友好                 | 外企常用     |
| Selenium   | 老牌，生态大                   | 国内存量多   |
| Appium     | 移动 App                       | 移动端       |

选 Playwright：自动等待减少不稳定，trace 能回放每一步，多浏览器支持好。

## 怎么做

- 只为最核心的 10～20 条用户流程写端到端测试（登录、搜索、下单、支付前确认），不追求覆盖所有页面
- 用 data-testid 和按文字、角色定位元素，页面改样式不会让测试失败
- PR 时在预览环境运行，失败时上传截图、录像和 Playwright trace，打开就能看到哪一步出错
- 不稳定的测试单独标记修复，不能简单地重试到通过

## 实施步骤

| 步骤 | 做什么                            | 怎么验证                |
| ---- | --------------------------------- | ----------------------- |
| 1    | 挑出核心用户流程                  | 有一份 10～20 条的清单  |
| 2    | 前端关键元素加 data-testid        | 定位不依赖样式          |
| 3    | 编写测试，本地跑通                | 全部通过                |
| 4    | CI 在预览环境运行，失败上传 trace | 失败时能打开 trace 查看 |
| 5    | 统计不稳定测试并修复              | 重试率逐步下降          |

## 关键代码

示例代码（简化），没有在生产环境运行：

```ts
import { test, expect } from '@playwright/test';

test('用户能下单', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('手机号').fill(process.env.TEST_USER!);
  await page.getByLabel('密码').fill(process.env.TEST_PASS!);
  await page.getByRole('button', { name: '登录' }).click();
  await page.getByTestId('product-1001').getByRole('button', { name: '加入购物车' }).click();
  await page.getByRole('link', { name: '去结算' }).click();
  await expect(page.getByText('确认订单')).toBeVisible();
});
```

## 效果指标

| 指标             | 做之前           | 预期效果（估算） |
| ---------------- | ---------------- | ---------------- |
| 回归测试         | 手工半天（估算） | 自动十几分钟     |
| 前端改坏其他页面 | 上线后发现       | PR 里发现        |
| 测试人员时间     | 重复点击         | 探索性测试       |

核心流程每次改动都被自动验证，测试人员从重复点击转向探索性测试。

## 常见坑

- **测试不稳定，时好时坏**：等待不当、测试数据互相影响。用自动等待和断言，每个测试准备独立数据。
- **测试太多太慢**：什么都写成 E2E。只测核心流程，细节交给单元测试和接口测试。
- **页面改版大量失败**：选择器依赖 CSS 类名。用 data-testid 和角色定位。

## AI 视角

**🤖 AI 是核心**

- **AI 能做什么**：根据需求描述生成测试脚本；页面改版后自动修复选择器；探索式测试找新问题
- **不该交给 AI**：核心流程的断言必须由人确定，不能让 AI 决定什么算通过
- **怎么落地**：用 AI 生成和维护脚本，断言人审核；Playwright 已提供生成测试的工具

## 面试怎么讲

30 秒讲法（方案思路；没有实际落地，面试时如实说明是设计过的方案）：

> 我会只为最核心的十几条用户流程写 Playwright 端到端测试，比如登录、搜索、下单，用 data-testid 和按角色定位元素；PR 时在预览环境运行，失败上传截图、录像和 trace。测试金字塔里 E2E 放在最顶层、数量最少，细节交给单元测试和接口测试。

常见追问：

**问：什么是测试金字塔？**

答：底层大量快速的单元测试，中间接口测试，顶层少量端到端测试；越往上越慢越脆弱。

**问：怎么处理不稳定的测试？**

答：找根因：等待条件、数据隔离、外部依赖；不能用无限重试掩盖。

**问：E2E 测试数据怎么准备？**

答：每个测试通过接口创建自己的数据，结束后清理，测试之间互不依赖。

**被问到「能不能用 AI」时：** UI 测试维护成本高，AI 能生成脚本、修复失效的选择器，大幅降低维护量，但断言要人定。
