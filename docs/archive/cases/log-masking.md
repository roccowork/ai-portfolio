## 问题

日志里打印了完整的手机号和身份证号，所有能看日志的人都能看到，违反个人信息保护法，也是数据泄露的常见来源。

## 适用场景

- 适合：处理个人信息的业务（电商、金融、医疗、政务）
- 不值得：日志里没有个人信息的内部工具
- 前提：日志集中采集，能在采集环节加处理

## 工具选型

| 方案                                | 特点                     | 适用         |
| ----------------------------------- | ------------------------ | ------------ |
| Grafana Alloy / Fluent Bit 处理规则 | 采集层统一脱敏           | 国内外都常用 |
| 应用日志框架脱敏（logback 插件）    | 源头脱敏                 | Java         |
| Vector                              | 高性能日志管道，VRL 脚本 | 开源         |
| 云日志服务脱敏                      | 托管                     | 云上         |

源头规范 + 采集层兜底：开发规范减少问题，采集层正则保证漏网的也被打码。

## 怎么做

- 从源头要求：开发规范禁止打印完整个人信息，代码审查时检查
- 采集层兜底：日志采集器（Alloy、Fluent Bit）用正则把手机号替换成 `138****5678`、身份证只保留前 6 后 4
- 每周用正则扫描一次已存储的日志，统计漏网的敏感信息，反馈给对应应用修复
- 有权限看原始数据的人和场景单独审批

## 实施步骤

| 步骤 | 做什么                             | 怎么验证                   |
| ---- | ---------------------------------- | -------------------------- |
| 1    | 制定日志规范：禁止打印完整个人信息 | 写进开发规范和代码审查清单 |
| 2    | 采集器配置正则替换                 | 测试日志里的手机号被打码   |
| 3    | 覆盖手机号、身份证、银行卡、邮箱   | 每种格式都有测试样例       |
| 4    | 每周扫描已存储日志统计漏网         | 报告发给对应应用负责人     |
| 5    | 原始数据访问单独审批               | 需要时走审批               |

## 关键代码

示例代码（简化），没有在生产环境运行：

```text
// Grafana Alloy：写入 Loki 前替换敏感信息
loki.process "mask" {
  stage.replace {
    expression = "(1[3-9]\\d)\\d{4}(\\d{4})"
    replace    = "$1****$2"
  }
  forward_to = [loki.write.default.receiver]
}
```

## 效果指标

| 指标                 | 做之前   | 预期效果（估算） |
| -------------------- | -------- | ---------------- |
| 日志中的完整个人信息 | 大量存在 | 采集时打码       |
| 合规风险             | 高       | 降低             |
| 漏网监测             | 没有     | 每周扫描         |

日志里不再出现完整个人信息，降低泄露风险，满足合规要求。

## 常见坑

- **正则误伤，把订单号当成手机号打码**：订单号也是 11 位数字。正则加边界和上下文（如字段名），用样本测试误伤率。
- **JSON 日志里字段被拆开**：正则只处理单行文本。对结构化日志按字段名脱敏。
- **脱敏影响排查**：需要完整信息定位问题。保留部分位（如后 4 位），或用哈希做关联。

## AI 视角

**✨ AI 能增强**

- **AI 能做什么**：识别正则难以覆盖的敏感信息（自由文本里的地址、姓名）
- **不该交给 AI**：已知格式的脱敏用规则，确定且快
- **怎么落地**：规则先处理，抽样日志交给 AI 检查漏网

## 面试怎么讲

30 秒讲法（方案思路；没有实际落地，面试时如实说明是设计过的方案）：

> 日志里打印完整手机号和身份证号是常见的合规问题。我会从源头规范开发不打印个人信息，再在日志采集层用 Alloy 或 Fluent Bit 的替换规则兜底：手机号保留前 3 后 4，身份证保留前 6 后 4，银行卡只留后 4 位；每周扫描已存储的日志统计漏网的，反馈给对应应用修复。

常见追问：

**问：个人信息保护法对日志有什么要求？**

答：处理个人信息要最小必要、采取安全措施；日志里随意记录完整个人信息不符合要求。

**问：脱敏和加密有什么区别？**

答：脱敏是不可逆地隐藏部分信息；加密可以用密钥还原，适合需要原文的场景。

**问：如何既脱敏又能排查问题？**

答：保留部分位数，或用哈希值代替原文，同一个用户的哈希相同，可以关联查询。

**被问到「能不能用 AI」时：** 已知格式用正则，AI 用来抽查自由文本里漏网的个人信息。
