## 问题

接口改坏了要等用户反馈才知道；系统能扛多少并发没人说得清，大促前临时找人压测。

## 适用场景

- 适合：有对外接口、有大促或流量高峰的业务
- 不值得：访问量很小、接口很少变化的内部系统
- 前提：有和生产配置接近的预发布环境，有可重复使用的测试数据

## 工具选型

| 方案             | 特点                          | 适用               |
| ---------------- | ----------------------------- | ------------------ |
| k6               | 脚本用 JS，能做功能测试和压测 | 国内外都常用       |
| JMeter           | 图形界面，插件多              | 国内测试团队最常见 |
| Postman / Newman | 接口测试，团队协作            | 外企常用           |
| Locust           | 用 Python 写压测              | Python 团队        |

选 k6：同一套脚本既能在 PR 里做接口检查，又能加压做性能测试；阈值写在脚本里，不达标直接让 CI 失败。

## 怎么做

- 用 k6 写接口测试：登录、查询、下单等核心接口，检查状态码、返回字段和耗时，PR 里自动跑
- 每周日凌晨对预发布环境做一次压测：逐步加压到目标并发，记录 p95 延迟和错误率
- 结果写入 Grafana，和上周对比，p95 变慢 20% 以上或错误率超过 1% 就通知开发
- 压测只打预发布环境，测试数据单独准备，避免影响生产

## 实施步骤

| 步骤 | 做什么                          | 怎么验证                |
| ---- | ------------------------------- | ----------------------- |
| 1    | 梳理核心接口：登录、查询、下单  | 有一份接口清单和预期    |
| 2    | 写 k6 功能检查，PR 里低并发运行 | 改坏接口时 CI 失败      |
| 3    | 准备预发布环境和压测数据        | 预发布和生产配置一致    |
| 4    | 每周定时压测，结果写入 Grafana  | 能看到每周的 p95 曲线   |
| 5    | 设置回归阈值告警                | p95 变慢 20% 时收到通知 |

## 关键代码

示例代码（简化），没有在生产环境运行：

```js
import http from 'k6/http';
import { check } from 'k6';

export const options = {
  stages: [
    { duration: '2m', target: 100 },
    { duration: '5m', target: 100 },
  ],
  thresholds: { http_req_duration: ['p(95)<500'], http_req_failed: ['rate<0.01'] },
};
export default function () {
  const r = http.get(`${__ENV.BASE}/api/products?page=1`);
  check(r, { 'status 200': (res) => res.status === 200 });
}
```

| 指标           | 做之前       | 预期效果（估算） |
| -------------- | ------------ | ---------------- |
| 接口改坏的发现 | 用户反馈     | PR 合并前        |
| 系统容量       | 说不清       | 有每周压测数据   |
| 大促准备       | 临时找人压测 | 有历史基线可对比 |

接口问题在合并前发现；系统容量有数据，大促前心里有底。

## 常见坑

- **压测把生产打挂了**：压测地址配错或共用了下游服务。压测只打预发布；下游第三方接口用模拟服务。
- **压测机自己成了瓶颈**：单台压测机 CPU、带宽满了。监控压测机资源；用多台或 k6 分布式运行。
- **结果不稳定**：每次测试数据、缓存状态不同。固定测试数据，先预热再计时。

## AI 视角

**✨ AI 能增强**

- **AI 能做什么**：根据 OpenAPI 文档生成接口测试用例初稿；解读压测结果找瓶颈
- **不该交给 AI**：性能阈值和通过标准必须明确
- **怎么落地**：用 AI 生成用例，人审核后加入；压测报告附 AI 分析

## 面试怎么讲

30 秒讲法（方案思路；没有实际落地，面试时如实说明是设计过的方案）：

> 我会用 k6 写核心接口的脚本：PR 里低并发跑一遍，检查状态码、字段和耗时；每周日凌晨对预发布环境做阶梯加压，p95 和错误率写进 Grafana，和上周对比，变慢 20% 就通知开发。压测只打预发布，第三方接口用模拟服务，避免影响生产。

常见追问：

**问：压测关注哪些指标？**

答：吞吐量（每秒请求数）、延迟分位数（p95、p99）、错误率，以及服务器资源（CPU、内存、连接数），找到拐点。

**问：为什么看 p95 而不是平均值？**

答：平均值会被大量快请求掩盖，p95 反映大多数用户的体验，慢请求一眼可见。

**问：压测发现瓶颈怎么定位？**

答：看资源（CPU、内存、IO）、看数据库慢查询和连接池、看链路追踪里哪一段最慢。

**被问到「能不能用 AI」时：** AI 能根据接口文档批量生成测试用例初稿，但通过标准必须明确。
