## 做了什么

运维 Agent 有两种用法。一是在线问答：访客在 ops.liuxd.dev/ops-agent/ 提问，比如「服务器现在健康吗」，Agent 自己决定调用哪些工具，读取本站真实服务器的告警、资源和服务状态，再给出结论和依据。二是自愈：Alertmanager 的告警推给 Agent，它先用只读工具查原因，再从预先写好的操作清单里选一个处理办法，执行后检查有没有真的恢复，处理记录公开展示在值班台页面的「自愈记录」里。

## 技术实现

- 用大模型的函数调用（Function Calling）做多轮工具循环，最多 8 轮
- 工具包括：列出正在触发的告警、节点 CPU / 内存 / 磁盘概况、列出 Pod 的状态和重启次数、查看 K8s 事件、查看 Pod 日志、查运维手册
- 查运维手册（search_runbook）是一个 RAG 工具：把本站自己的运维手册、架构说明、迁移手册按标题切段做向量检索。问「怎么回滚」「证书签不下来怎么办」时，Agent 先查手册，按手册回答并注明出处章节；问实时状态时查监控和 K8s，两者不一致时以实时数据为准。处理告警时也能先查手册里的处理办法。手册有一套 24 道题的评测集
- 后端是 Python + FastAPI，K8s 和 Prometheus 通过 HTTP API 访问
- 需要人确认的操作通过 Telegram 机器人推送，带「执行」按钮

## 安全设计

安全边界靠程序，不靠模型自觉：

- 问答用的 K8s 账号只有只读权限，看不到 Secret；只能查白名单里的命名空间
- 日志先脱敏（IP、邮箱、长串密钥）再交给模型；公开演示只查指标和状态，不看日志和配置
- 自愈时模型只能「提议」清单里的 3 种操作，参数由代码校验，真正执行的是代码
- 补跑失败的备份、重建卡死的 Pod 这类低风险操作直接执行；重启服务等关键操作推到 Telegram，由人点「执行」才动手
- 自愈的 K8s 写权限只绑定在少数几个命名空间；Agent 不能动自己；同一个对象 6 小时内自动处理过一次还没好，就不再自动，交给人
- 每天自动分析的告警次数有上限，公开问答每人每天 10 次
