## 问题

CI 每次提交都推一个镜像，一年下来几千个版本、几百 G 磁盘，镜像仓库所在的磁盘突然写满，发布全部失败。

## 适用场景

- 适合：CI 频繁推镜像、自建镜像仓库的团队
- 不值得：使用云镜像仓库且有自动清理策略的
- 前提：镜像标签有规律（commit SHA、版本号）

## 工具选型

| 方案                   | 特点                 | 适用                     |
| ---------------------- | -------------------- | ------------------------ |
| Harbor 保留策略        | 界面配置，按规则保留 | 国内外都常用             |
| registry + 自写脚本    | 轻量自建仓库         | ✅ 实验 15 用的 registry |
| 云镜像仓库生命周期规则 | 托管                 | 云上                     |
| regctl / crane         | 命令行操作镜像仓库   | 脚本里使用               |

用 Harbor 就直接配保留策略；自建 registry 用脚本，额外保护线上正在使用的镜像。

## 怎么做

- Harbor 自带保留策略：按项目设置「保留最近 10 个标签 + 带 release 前缀的标签」，每天自动执行
- 自建 registry 用脚本实现：列出标签按时间排序，额外查询 K8s 里所有 Pod 正在用的镜像，确保线上版本不被删
- 删除标签后运行垃圾回收才会真正释放磁盘
- 清理报告：删除了多少个版本、释放了多少空间

## 实施步骤

| 步骤 | 做什么                                  | 怎么验证              |
| ---- | --------------------------------------- | --------------------- |
| 1    | 确定保留规则：最近 10 个 + release 标签 | 规则写成文档          |
| 2    | 查询 K8s 正在使用的镜像                 | 得到线上镜像列表      |
| 3    | 删除不需要的标签                        | 先 dry-run 打印要删的 |
| 4    | 运行垃圾回收释放磁盘                    | 磁盘空间下降          |
| 5    | 每周定时运行并报告                      | 收到清理报告          |

## 关键代码

示例代码（简化），没有在生产环境运行：

```python
in_use = {c.image for p in k8s.list_pod_for_all_namespaces().items for c in p.spec.containers}
for repo in registry.repositories():
    tags = sorted(registry.tags(repo), key=registry.created, reverse=True)
    for tag in tags[KEEP:]:
        if f"{REGISTRY}/{repo}:{tag}" not in in_use:
            registry.delete(repo, tag)
```

## 效果指标

| 指标               | 做之前           | 预期效果（估算） |
| ------------------ | ---------------- | ---------------- |
| 镜像仓库磁盘       | 持续增长直到写满 | 稳定             |
| 发布失败（磁盘满） | 偶发             | 消除             |
| 镜像数量           | 几千个版本       | 每个仓库约 10 个 |

镜像仓库磁盘稳定，不再因为磁盘满导致发布失败。实验 15 的本地 registry 就遇到过这个问题。

## 常见坑

- **删了线上正在用的镜像**：清理只看时间不看使用情况。排除 K8s 里正在使用和回滚可能用到的版本。
- **删了标签磁盘没减少**：只删除了引用。运行垃圾回收；registry 需要只读模式或停写。
- **多个标签指向同一个镜像**：按标签删会影响其他标签。按 digest 判断是否还被引用。

## AI 视角

**⚙️ 规则就够**

- **AI 能做什么**：基本不需要
- **不该交给 AI**：删除规则必须确定，绝不能误删线上镜像
- **怎么落地**：保持规则

## 面试怎么讲

30 秒讲法（方案思路；没有实际落地，面试时如实说明是设计过的方案）：

> 我会给镜像仓库设保留策略：每个仓库保留最近 10 个标签和带 release 前缀的标签。自建 registry 用脚本实现，并额外查询 K8s 里所有 Pod 正在用的镜像，确保线上和可回滚的版本不被删；删除标签后运行垃圾回收才会真正释放磁盘。实验 15 的本地 registry 就遇到过磁盘越来越大的问题。

常见追问：

**问：为什么删除标签后磁盘没有释放？**

答：标签只是指向镜像清单的引用，层文件还在，要运行垃圾回收才删除不再被引用的层。

**问：镜像标签用 latest 有什么问题？**

答：无法知道运行的是哪个版本，回滚困难，缓存也可能拉到旧镜像。用 commit SHA 或版本号。

**问：怎么减小镜像体积？**

答：多阶段构建、精简基础镜像（alpine、distroless）、合并层、清理包管理器缓存。

**被问到「能不能用 AI」时：** 涉及删除的自动化必须确定，不用 AI。
