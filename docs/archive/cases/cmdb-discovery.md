## 问题

手工维护的 CMDB 很快就和实际对不上：新机器没登记、下线的机器还在表里。出故障时查不到「这台机器是谁的、跑了什么」。

## 适用场景

- 适合：服务器、云资源上百个，多人维护的环境
- 不值得：十几台机器，一张表就能管住
- 前提：资源都有 API 可查（云、虚拟化、K8s）

## 工具选型

| 方案            | 特点                     | 适用         |
| --------------- | ------------------------ | ------------ |
| NetBox          | 开源，资产和网络建模     | 国内外都常用 |
| 蓝鲸 CMDB       | 国产开源，和作业平台一体 | 国内常用     |
| ServiceNow CMDB | 商业，ITSM 一体          | 外企常用     |
| Excel           | 零成本                   | 十几台以内   |

选 NetBox：数据模型完整、API 好用，采集脚本写入后其他系统都能读取。

## 怎么做

- 数据从源头自动采集：云厂商 API（实例、IP、标签）、vCenter/PVE（虚拟机）、K8s API（Deployment、Service）
- 每小时和 CMDB（如 NetBox）对比：新增的自动录入，变化的更新，消失的标记为下线而不是直接删除
- 负责人、业务线取自资源标签，没有标签的列成清单提醒补齐
- 告警、巡检、作业平台都从 CMDB 读取主机分组，不再各维护一份清单

## 实施步骤

| 步骤 | 做什么                                            | 怎么验证                       |
| ---- | ------------------------------------------------- | ------------------------------ |
| 1    | 部署 NetBox，定义站点、角色、自定义字段（负责人） | 界面能手动录入一台主机         |
| 2    | 写采集脚本：云 API、PVE、K8s                      | 脚本输出资源清单               |
| 3    | 对比后新增、更新、标记下线                        | 重复运行结果不变               |
| 4    | 定时每小时运行                                    | 新建云主机 1 小时内出现在 CMDB |
| 5    | 其他系统改为从 CMDB 读清单                        | 巡检、作业平台使用同一份数据   |

## 常见坑

- **同一资源重复录入**：不同来源名称不一致。用唯一 ID（云实例 ID、序列号）作为主键。
- **资源下线后被误删记录**：采集失败时当成全部下线。采集失败时跳过对比；下线只标记不删除。
- **负责人标签缺失**：创建资源时没要求。Terraform 统一加标签，缺失的定期列出来。

## AI 视角

**✨ AI 能增强**

- **AI 能做什么**：根据主机名、标签、进程推断资源属于哪个业务和负责人
- **不该交给 AI**：资产主数据以采集结果为准，AI 推断只作为待确认建议
- **怎么落地**：AI 给出归属建议，负责人确认后写入

## 面试怎么讲

30 秒讲法（方案思路；没有实际落地，面试时如实说明是设计过的方案）：

> 我会以 NetBox 作为 CMDB，但数据不靠人填：采集脚本每小时从云 API、虚拟化平台和 K8s API 拉取资源，用实例 ID 做主键对比，新增的录入、变化的更新、消失的只标记下线。负责人来自资源标签，缺失的列清单提醒补齐。巡检、作业平台都从 CMDB 读主机分组。

常见追问：

**问：CMDB 最大的难点是什么？**

答：数据准确。靠人维护一定会过时，必须从源头自动采集，人只补充采集不到的信息。

**问：CMDB 和监控系统怎么配合？**

答：监控的目标清单从 CMDB 生成，告警里带上 CMDB 的负责人和业务线。

**问：如何处理采集失败？**

答：某个来源失败时不做对比，避免把它的资源全部误判为下线；同时告警。

**被问到「能不能用 AI」时：** CMDB 数据靠采集，AI 帮忙补全「这台机器属于哪个业务」这类采集不到的信息，需要人确认。
