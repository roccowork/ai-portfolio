## 问题

全量测试太慢不能每个 PR 都跑，于是只在发版前跑，一跑发现几十个失败，根本说不清是哪天哪个提交改坏的。

## 适用场景

- 适合：测试用例多、全量跑一次要几十分钟以上的项目
- 不值得：测试几分钟就能跑完的小项目（每个 PR 都跑全量即可）
- 前提：有稳定的测试环境和自动化用例

## 工具选型

| 方案                          | 特点           | 适用            |
| ----------------------------- | -------------- | --------------- |
| GitHub Actions 定时 / Jenkins | 触发和执行     | 国内 Jenkins 多 |
| Allure Report                 | 报告和历史趋势 | 国内外都常用    |
| pytest / JUnit                | 测试框架       | 按语言          |
| TestRail                      | 用例管理       | 外企常用        |

定时任务 + Allure 足够；关键是报告要突出「新失败」而不是全部失败。

## 怎么做

- PR 里只跑快速的冒烟测试，每天夜里对主分支最新代码跑全量接口和 UI 测试
- 用 Allure 生成报告，保留历史趋势，标出「昨天通过今天失败」的新失败用例
- 早上把通过率、新失败用例和最近的相关提交推到群里，对应开发当天修复
- 不稳定的测试单独统计，不计入通过率，安排专人修复

## 实施步骤

| 步骤 | 做什么                     | 怎么验证       |
| ---- | -------------------------- | -------------- |
| 1    | 区分冒烟测试和全量测试     | PR 只跑冒烟    |
| 2    | 配置夜间定时任务           | 每天按时运行   |
| 3    | 生成 Allure 报告并保留历史 | 能看到趋势图   |
| 4    | 计算新失败用例并推送       | 早上群里有报告 |
| 5    | 不稳定用例单独统计         | 通过率不受干扰 |

## 关键代码

示例代码（简化），没有在生产环境运行：

```yaml
on:
  schedule: [{ cron: '0 18 * * *' }] # UTC 18:00 = 北京时间 02:00
jobs:
  regression:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - run: ./deploy-to-test.sh
      - run: pytest tests/ --alluredir=allure-results || true
      - run: allure generate allure-results -o report && python notify.py report/
```

## 效果指标

| 指标              | 做之前         | 预期效果（估算）     |
| ----------------- | -------------- | -------------------- |
| 问题发现时间      | 发版前集中发现 | 第二天               |
| 定位引入提交      | 说不清         | 范围缩小到一天的提交 |
| 发版前修 bug 压力 | 大             | 分散到每天           |

问题在引入的第二天就被发现，发版前不再集中爆雷。

## 常见坑

- **测试环境不稳定导致大面积失败**：环境本身有问题。测试前做环境健康检查，环境异常时报告环境问题。
- **报告没人看**：只发通过率。突出新失败用例并 @ 相关提交的作者。
- **时区导致时间错乱**：cron 用 UTC。注释写清换算，或用支持时区的调度器。

## AI 视角

**✨ AI 能增强**

- **AI 能做什么**：对新失败的用例自动分析：是产品缺陷、脚本问题还是环境问题
- **不该交给 AI**：通过率统计必须确定
- **怎么落地**：新失败用例附 AI 分类和可能原因

## 面试怎么讲

30 秒讲法（方案思路；没有实际落地，面试时如实说明是设计过的方案）：

> PR 里只跑快速的冒烟测试，每天夜里对主分支跑全量接口和 UI 测试，用 Allure 生成报告并保留历史，算出昨天通过今天失败的新失败用例，早上推到群里并附上相关提交。这样问题在引入第二天就被发现，不会到发版前集中爆雷。

常见追问：

**问：冒烟测试和回归测试的区别？**

答：冒烟测试只验证最基本的功能能用，快；回归测试验证已有功能没被改坏，全面但慢。

**问：为什么要突出新失败？**

答：长期失败的用例大家已经知道，新失败才说明昨天的改动引入了问题。

**问：测试通过率低怎么办？**

答：先分类：产品缺陷、测试脚本问题、环境问题、不稳定用例，分别处理。

**被问到「能不能用 AI」时：** 回归报告里最费时的是分析失败原因，AI 先做一轮分类。
