## 问题

主从复制搭好了，但真正主库挂了的时候，没人敢切、不知道怎么切，切完应用连不上；切换步骤只在某个人脑子里。

## 适用场景

- 适合：数据库是核心、要求停机时间短的业务
- 不值得：可以接受几小时停机、直接从备份恢复的系统
- 前提：已有主从复制（最好是 GTID）、VIP 或 DNS 切换手段

## 工具选型

| 方案             | 特点                     | 适用        |
| ---------------- | ------------------------ | ----------- |
| Ansible playbook | 步骤可控，有检查点       | ✅ 方案采用 |
| Orchestrator     | MySQL 拓扑管理和自动切换 | 国内外都用  |
| MHA              | 老牌 MySQL 高可用        | 国内存量多  |
| 云数据库高可用版 | 托管自动切换             | 云上        |

用 Ansible：切换步骤透明、每步可以检查和暂停，适合先把手动流程固化下来；成熟后再考虑 Orchestrator 自动切换。

## 怎么做

- 切换步骤写成 Ansible playbook：检查从库已应用完所有 GTID → 停止复制 → 关闭 read_only → 切换 VIP（或改 DNS）→ 应用健康检查
- 每一步都有检查点，不满足条件就停下来等人确认，避免数据丢失
- 每季度在维护窗口完整演练一次，记录实际切换时间（RTO）和丢失的数据量（RPO）
- 实验 03 搭过 GTID 主从、实验 10 搭过 Keepalived VIP，这是两者结合的自动化

## 实施步骤

| 步骤 | 做什么                    | 怎么验证               |
| ---- | ------------------------- | ---------------------- |
| 1    | 写清楚切换前提和步骤      | 文档评审通过           |
| 2    | 写 playbook，每步带检查点 | 在测试环境跑通         |
| 3    | 切换 VIP 或 DNS           | 应用连接到新主库       |
| 4    | 季度演练，记录 RTO 和 RPO | 演练报告里有实际耗时   |
| 5    | 演练后恢复原拓扑          | 原主库作为从库重新加入 |

## 关键代码

示例代码（简化），没有在生产环境运行：

```yaml
- name: 确认从库已应用全部日志
  community.mysql.mysql_replication: { mode: getreplica }
  register: r
  failed_when: r.Retrieved_Gtid_Set != r.Executed_Gtid_Set
- name: 提升为主库
  community.mysql.mysql_query:
    query:
      [
        STOP REPLICA,
        RESET REPLICA ALL,
        SET GLOBAL super_read_only = OFF,
        SET GLOBAL read_only = OFF,
      ]
```

## 效果指标

| 指标            | 做之前                       | 预期效果（估算）             |
| --------------- | ---------------------------- | ---------------------------- |
| 切换耗时（RTO） | 凭经验，可能几十分钟（估算） | 几分钟，每季度验证           |
| 数据丢失（RPO） | 未知                         | 切换前确认从库已应用全部日志 |
| 切换依赖个人    | 只有某个人会                 | 任何值班人员按脚本执行       |

切换从「凭经验」变成「按脚本」，每季度验证一次，真出事时心里有底。

## 常见坑

- **切换后应用还连着旧主库**：应用缓存了连接或写死了 IP。用 VIP 或 DNS，应用配置连接重试。
- **旧主库恢复后出现两个主库**：旧主库没有设成只读。切换时隔离旧主库；恢复后作为从库加入。
- **从库延迟大时强行切换**：丢数据。检查 GTID 是否全部应用，不满足时等待或人工决策。

## AI 视角

**✨ AI 能增强**

- **AI 能做什么**：演练后根据日志生成演练报告和改进建议
- **不该交给 AI**：是否切换、切换步骤必须由人和脚本决定
- **怎么落地**：演练结束后用 AI 生成报告初稿

## 面试怎么讲

30 秒讲法（方案思路；没有实际落地，面试时如实说明是设计过的方案）：

> 我会把 MySQL 主从切换写成 Ansible playbook：先确认从库已经应用了所有 GTID，再停复制、关闭只读、切换 VIP，最后检查应用健康，每一步都有检查点，不满足就停下来等人确认。每季度在维护窗口演练一次，记录实际的 RTO 和 RPO。这是实验 03 的 GTID 主从和实验 10 的 Keepalived VIP 结合起来的自动化。

常见追问：

**问：RTO 和 RPO 是什么？**

答：RTO 是恢复时间目标（多久恢复服务），RPO 是恢复点目标（最多丢多少数据）。

**问：GTID 对切换有什么帮助？**

答：每个事务有全局唯一 ID，能精确判断从库是否已经应用了主库的全部事务，换主时也不用找 binlog 位置。

**问：怎么防止脑裂（两个主库）？**

答：切换时把旧主库设为只读或隔离网络；VIP 用单播心跳，网络分区时有仲裁。

**被问到「能不能用 AI」时：** 切换必须人决策、脚本执行；AI 只帮写演练报告。
