## 问题

订单、通知走消息队列异步处理。消费者挂了或变慢，消息越堆越多，用户只觉得「短信怎么还没来」，等发现时已经积压几十万条。

## 适用场景

- 适合：用消息队列做异步处理的业务（订单、通知、日志）
- 不值得：没有用消息队列的系统
- 前提：消息队列有可采集的指标

## 工具选型

| 方案                                      | 特点                              | 适用         |
| ----------------------------------------- | --------------------------------- | ------------ |
| kafka_exporter / RabbitMQ Prometheus 插件 | 标准指标                          | 国内外都常用 |
| Burrow                                    | LinkedIn 出品，专门评估消费者状态 | Kafka        |
| 云消息队列自带监控                        | 托管                              | 云上         |
| KEDA                                      | 按积压自动扩容消费者              | K8s          |

选 Prometheus 体系：和现有告警通道统一，积压趋势可以用 PromQL 表达，还能直接驱动 KEDA 扩容。

## 怎么做

- kafka_exporter 采集每个消费组的 lag（积压条数）；RabbitMQ 用自带的 Prometheus 插件采集队列长度
- 告警看「趋势」而不只看数值：积压 10 分钟内持续增长、或者预计 30 分钟内处理不完
- 告警附上生产速率和消费速率，一眼判断是生产暴增还是消费者变慢
- 无状态的消费者用 KEDA 按积压量自动扩容

## 实施步骤

| 步骤 | 做什么                                       | 怎么验证                     |
| ---- | -------------------------------------------- | ---------------------------- |
| 1    | 部署 kafka_exporter 或启用 RabbitMQ 插件     | Prometheus 里能看到 lag 指标 |
| 2    | 为核心消费组建看板：积压、生产速率、消费速率 | 看板上能看出谁快谁慢         |
| 3    | 写趋势告警：积压持续增长 10 分钟             | 停掉消费者时触发             |
| 4    | 无状态消费者接入 KEDA                        | 积压增加时 Pod 数增加        |
| 5    | 设置消费者数量上限                           | 不超过分区数                 |

## 关键代码

示例代码（简化），没有在生产环境运行：

```yaml
- alert: KafkaConsumerLagGrowing
  expr: sum by (consumergroup) (delta(kafka_consumergroup_lag[10m])) > 0
    and sum by (consumergroup) (kafka_consumergroup_lag) > 10000
  for: 10m
  annotations:
    summary: '消费组 {{ $labels.consumergroup }} 积压持续增长'
```

## 效果指标

| 指标     | 做之前               | 预期效果（估算）         |
| -------- | -------------------- | ------------------------ |
| 积压发现 | 用户投诉「消息没来」 | 10 分钟内                |
| 判断原因 | 逐个排查             | 看板上对比生产和消费速率 |
| 处理积压 | 人工加机器           | KEDA 自动扩容            |

积压在影响用户之前就被发现和处理。

## 常见坑

- **扩容消费者没有效果**：Kafka 消费者数量超过分区数后多出来的空闲。分区数决定并行上限，提前规划分区。
- **积压阈值误报**：业务高峰时短暂积压是正常的。用趋势（持续增长）而不是固定数值。
- **消费者重启后重复消费**：位移提交时机不对。消费逻辑做成幂等。

## AI 视角

**✨ AI 能增强**

- **AI 能做什么**：结合积压趋势和消费者日志，判断是生产暴增还是消费变慢
- **不该交给 AI**：扩容上限和告警阈值要按规则设置
- **怎么落地**：告警附 AI 对生产、消费速率的解读

## 面试怎么讲

30 秒讲法（方案思路；没有实际落地，面试时如实说明是设计过的方案）：

> 我会用 kafka_exporter 采集每个消费组的积压量，告警看趋势而不只看数值：积压 10 分钟内持续增长、并且超过一定数量才告警，告警里附上生产和消费速率，一眼判断是生产暴增还是消费变慢。无状态消费者用 KEDA 按积压量自动扩容，上限是分区数。

常见追问：

**问：Kafka 消费积压怎么处理？**

答：先看原因：消费者挂了就恢复；消费慢就扩容（不超过分区数）或优化消费逻辑；临时可以把消息转到更多分区的新 topic 加快处理。

**问：为什么消费者数量不能超过分区数？**

答：一个分区同一时间只能被同一消费组里的一个消费者消费，多出来的消费者会空闲。

**问：如何保证消息不重复处理？**

答：Kafka 默认至少一次，消费逻辑要幂等（用业务 ID 去重）。

**被问到「能不能用 AI」时：** 积压告警靠趋势规则，AI 帮我快速判断是生产端还是消费端的问题。
