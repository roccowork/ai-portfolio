## 问题

指标告警只能发现「慢了、挂了」，很多问题（支付回调失败、第三方接口报错）只出现在日志里。没有集中日志时，排查要一台台登录服务器 grep。

## 适用场景

- 适合：微服务、容器化环境，问题需要靠日志定位的系统
- 不值得：服务很少、直接 journalctl 就能看完的
- 前提：日志输出到标准输出或固定文件，最好是结构化（JSON）

## 工具选型

| 方案                    | 特点                   | 适用           |
| ----------------------- | ---------------------- | -------------- |
| Loki + Alloy            | 只索引标签，存储便宜   | 国内外都常用   |
| ELK / OpenSearch        | 全文检索强，资源消耗大 | 国内大厂存量多 |
| 阿里云 SLS / 腾讯云 CLS | 托管服务               | 国内云上常用   |
| Datadog / Splunk        | 商业，功能全           | 外企常用       |

选 Loki：和 Prometheus、Grafana 同一套体系，资源占用比 ELK 小很多，告警规则写法类似 PromQL。

## 怎么做

- Alloy 以 DaemonSet 运行，采集所有容器日志，打上命名空间、应用标签后写入 Loki
- Loki 的 Ruler 用 LogQL 定义告警：某应用 5 分钟内 ERROR 超过 10 条、出现 OOM、出现特定关键字
- 告警经 Alertmanager 走现有的企业微信转发器，和指标告警同一个群
- 日志只保留 7 天，单节点用文件存储即可

## 关键代码

示例代码（简化），没有在生产环境运行：

```yaml
groups:
  - name: app-logs
    rules:
      - alert: AppErrorLogsHigh
        expr: sum by (app) (count_over_time({namespace="prod"} |= "ERROR" [5m])) > 10
        for: 2m
        labels: { severity: warning }
```

## 常见坑

- **标签太多导致 Loki 变慢**：把用户 ID、请求 ID 做成了标签。标签只用命名空间、应用等低基数字段，其余放日志内容里。
- **多行日志（Java 异常栈）被拆成很多条**：采集器按行切分。配置多行合并规则。
- **Promtail 停止维护**：2026 年起不再更新。改用 Grafana Alloy（实验 14 已采用）。

## AI 视角

**✨ AI 能增强**

- **AI 能做什么**：把相似的错误日志聚类，告诉你「今天新出现了哪类错误」；用自然语言生成 LogQL 查询
- **不该交给 AI**：告警触发条件要明确可测，不能让模型临时决定什么算异常
- **怎么落地**：每天对 ERROR 日志做聚类摘要推送；Grafana 里接 AI 助手帮写查询

## 面试怎么讲

30 秒讲法（方案思路；没有实际落地，面试时如实说明是设计过的方案）：

> 我在实验环境用 Helm 装过 Loki 和 Alloy：Alloy 以 DaemonSet 采集所有容器日志，打上命名空间和应用标签写入 Loki。告警用 Loki Ruler 写 LogQL，比如某应用 5 分钟内 ERROR 超过 10 条，走现有 Alertmanager 发到企业微信。标签只用低基数字段，否则 Loki 会变慢。

常见追问：

**问：Loki 和 ELK 的区别？**

答：Loki 只索引标签不索引全文，存储和内存成本低，查询靠标签缩小范围后再过滤；ELK 全文索引，搜索更强但资源消耗大。

**问：什么是高基数标签？为什么要避免？**

答：取值非常多的标签（用户 ID、请求 ID），会产生大量日志流，索引膨胀、查询变慢。

**问：日志告警和指标告警怎么分工？**

答：指标告警发现「慢了、挂了」，日志告警发现特定错误（支付失败、第三方报错）；能做成指标的尽量做成指标。

**被问到「能不能用 AI」时：** 日志告警规则保持明确，AI 用来做「今天新出现了哪些错误模式」的聚类摘要。
