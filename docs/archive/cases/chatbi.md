## 问题

业务人员想知道「上月哪个区域销售额下滑最多」「新客户复购率是多少」，要提需求给数据分析师，排队几天；固定报表又回答不了临时的问题。不同人算出来的数还经常对不上，因为口径不一样。

## 适用场景

- 适合：已有数据仓库或分析库、临时取数需求多的公司
- 不值得：数据还散落在各个 Excel 里、没有统一数据库的
- 前提：有数据仓库（或业务库的只读副本）；核心指标的口径已经定义清楚

## 工具选型

| 方案                                      | 特点               | 适用         |
| ----------------------------------------- | ------------------ | ------------ |
| 自写：语义层 + 大模型生成 SQL             | 可控，可接私有模型 | ✅ 方案采用  |
| 帆软 FineChatBI、阿里云 Quick BI 智能小 Q | 和国产 BI 集成     | 国内常用     |
| Power BI Copilot、Tableau Pulse           | 和 BI 平台集成     | 外企常用     |
| Vanna、WrenAI 等开源 Text-to-SQL          | 可自建             | 有开发能力时 |

成败不在模型，而在**语义层**：把「销售额」「新客户」「复购率」的计算口径写成定义，AI 只能用这些定义组合查询，而不是自由地猜表和字段。

## 怎么做

- **建语义层**：每个指标写清楚定义——来自哪张表、怎么计算、默认过滤条件（如「销售额」不含退款）；维度写清楚可选值（区域、产品线、渠道）
- **生成 SQL**：用户提问后，先匹配语义层里的指标和维度，再让大模型生成 SQL；匹配不到的指标直接回答「没有这个指标的定义」，不猜
- **安全执行**：只读账号、只允许 SELECT、自动加 LIMIT 和超时；按用户身份加行级权限（销售只能看自己区域）
- **结果展示**：自动选择图表类型（趋势用折线、对比用柱状），同时展示 SQL 和使用的口径，用户可以核对
- 好的问答可以一键保存为固定报表

## 关键代码

示例代码（简化），没有在生产环境运行。语义层定义：

```yaml
metrics:
  sales_amount:
    label: 销售额
    sql: SUM(order_amount) - SUM(refund_amount)
    table: dw.fact_orders
    filters: ["order_status = 'paid'"]
dimensions:
  region: { label: 区域, column: region_name }
  month: { label: 月份, column: "DATE_TRUNC('month', paid_at)" }
```

生成和执行：

```python
plan = llm.complete(PLAN_PROMPT.format(question=q, semantic=SEMANTIC), response_format=PLAN_SCHEMA)
if plan.unknown_metrics:
    return f"没有这些指标的定义：{plan.unknown_metrics}，请联系数据团队"
sql = build_sql(plan, SEMANTIC, row_filter=user.region_filter)  # 由程序拼接，口径来自定义
rows = readonly_db.query(sql, timeout=30, limit=10000)
return chart(rows, plan.chart_type), sql
```

## 常见坑

- **让 AI 直接看所有表自由生成 SQL**：字段含义猜错，数看起来对其实错。用语义层约束，只用定义好的指标。
- **答错了没人发现**：用户不懂 SQL。展示口径说明，关键数据和固定报表交叉核对。
- **权限漏洞**：问一句话就看到了别的区域的数据。行级权限由程序强制加，不依赖 AI。
- **大查询拖垮数据库**：全表扫描。只连只读副本，加超时和 LIMIT。
- **没有评测集**：改了提示词不知道变好还是变坏。维护真实问题的评测集，每次改动都跑一遍。

## AI 视角

**🤖 AI 是核心**

- **AI 能做什么**：理解口语化的问题（「上个月」「卖得最差的」），对应到指标和维度，选择合适的图表，用文字总结结论
- **不该交给 AI**：指标口径的定义、数据权限、SQL 的安全检查
- **怎么落地**：语义层定口径、AI 理解问题、程序拼 SQL 和加权限、人可以核对 SQL

## 面试怎么讲

30 秒讲法（方案思路；没有实际落地，面试时如实说明是设计过的方案）：

> 我会先和业务整理二三十个核心指标的口径，写成语义层定义。用户提问时，AI 只负责把问题对应到指标、维度和时间范围，SQL 由程序根据定义拼出来，并强制加上行级权限、超时和 LIMIT，在只读副本上执行。结果自动画图，同时展示 SQL 和口径。上线前准备 100 个真实问题的评测集，每次改动都跑一遍看准确率。

常见追问：

**问：为什么不让 AI 直接写 SQL？**

答：AI 不知道字段的真实含义和业务口径，容易写出能运行但结果错误的 SQL；用语义层约束能保证口径一致。

**问：数据权限怎么保证？**

答：按用户身份由程序强制加过滤条件，只读账号，只允许 SELECT；不依赖 AI 自觉遵守。

**问：怎么评估准确率？**

答：收集真实问题，人工写标准答案，比较查询结果是否一致；答错的问题分析原因，补充口径或改进提示词。

**被问到「能不能用 AI」时：** 这个案例本身就是 AI；关键是语义层管口径，程序管权限。
