## 问题

单台云服务器上跑着云盘、访问统计、监控配置。服务器坏了、被误删、被勒索，数据就没了。备份脚本跑失败了也没人知道。

## 适用场景

- 适合：任何有数据的系统。尤其是单台服务器、没有专职 DBA 的小团队
- 不值得：数据随时可以从别处重建的（比如纯缓存、构建产物）
- 前提：有一个和生产不在同一处的存储（另一家云、另一个机房、NAS）

## 工具选型

| 方案       | 特点                         | 适用                         |
| ---------- | ---------------------------- | ---------------------------- |
| restic     | 加密、去重、增量，单个二进制 | ✅ 本站选用                  |
| Velero     | 备份整个 K8s 资源和卷        | K8s 集群级备份               |
| BorgBackup | 压缩率高                     | 需要 SSH 访问的远端          |
| 云厂商快照 | 整盘快照，一键回滚           | 和服务器在同一家云，不算异地 |

选 restic：原生支持 S3 协议（R2），加密和去重内置，单个命令就能备份和恢复；只备份应用数据，比整盘快照省空间。

## 怎么做

- 每个应用一个备份 CronJob，共用同一套脚本（Git 里的 ConfigMap）
- **SQLite 不能直接复制**：正在写入的数据库文件拷出来可能是坏的，先用 init 容器做一致性快照，备份快照而不是原文件
- restic 加密后传到 Cloudflare R2：和服务器不在同一家云，服务器所在的云出问题也不影响备份
- 保留最近 7 天、4 周、6 个月各一份，每次备份后 `restic check` 检查仓库结构
- 密钥只放在集群 Secret 里，由人手动创建；restic 密码另存一份在仓库和服务器之外，丢了就无法解密
- **失败告警**：备份 Job 失败，或者超过 26 小时没有成功，都会推到企业微信

## 实施步骤

| 步骤 | 做什么                                        | 怎么验证                                            |
| ---- | --------------------------------------------- | --------------------------------------------------- |
| 1    | 开通 Cloudflare R2，建桶和只限该桶的 API 令牌 | 用 restic init 能初始化仓库                         |
| 2    | 写通用备份脚本放进 ConfigMap，各应用复用      | 脚本变化不需要重建镜像                              |
| 3    | SQLite 应用加 init 容器做一致性快照           | 快照文件 `PRAGMA integrity_check` 返回 ok           |
| 4    | 每个应用一个 CronJob，`--host` 写死应用名     | `restic snapshots --host <应用>` 只显示该应用的快照 |
| 5    | 配置保留策略和 `restic check`                 | 日志里看到 forget、check 通过                       |
| 6    | 加两个告警：Job 失败、超过 26 小时没成功      | 手动让备份失败一次，群里收到告警                    |

## 关键代码

```sh
# 正在使用的数据库文件不直接备份，用 /snapshot 里的一致性副本代替
set -- --exclude '/data/*.db' --exclude '/data/*.db-wal' --exclude '/data/*.db-shm'
restic backup --host "$BACKUP_HOST" "$@" /data /snapshot
restic forget --host "$BACKUP_HOST" --keep-daily 7 --keep-weekly 4 --keep-monthly 6 --prune
restic check
```

```yaml
- alert: BackupStale
  expr: time() - kube_cronjob_status_last_successful_time{cronjob=~"backup-.*"} > 26 * 3600
```

## 常见坑

- **`--host` 必须写死**：Pod 名每次都不同，用默认主机名的话，保留策略没法按应用分组，旧快照永远删不掉。

## AI 视角

**⚙️ 规则就够**

- **AI 能做什么**：基本不需要；可以解读恢复演练报告
- **不该交给 AI**：备份和保留策略必须是确定的

## 面试怎么讲

30 秒讲法：

> 服务器上的云盘、访问统计、监控配置每天用 restic 加密备份到 Cloudflare R2，和服务器不在同一家云。SQLite 不能直接复制，我先用 init 容器做一致性快照，备份快照而不是原文件。保留 7 天、4 周、6 个月各一份，每次备份后做仓库检查。有两个告警：Job 失败和超过 26 小时没有成功。恢复演练是下一步，做完会补上恢复耗时。

常见追问：

**问：什么是 3-2-1 原则？你做到了吗？**

答：3 份数据、2 种介质、1 份异地。现在是生产数据 + R2 异地加密备份，异地做到了；第三份副本还没有，计划加一份本地 NAS。

**问：为什么正在用的 SQLite 不能直接复制？**

答：WAL 模式下数据分散在主文件和 WAL 文件里，复制过程中有写入就可能得到半新半旧、打不开的文件。用 SQLite 的在线备份接口生成一致副本。

**问：为什么阈值是 26 小时而不是 24？**

答：备份每天跑一次，每次耗时不同，留 2 小时余量，避免正常的时间抖动触发告警。

**被问到「能不能用 AI」时：** 备份是确定性最重要的场景，不引入 AI。
