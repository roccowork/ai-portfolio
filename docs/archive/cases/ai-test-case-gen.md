## 问题

- **功能测试**：每个需求测试人员要从头写测试用例，大量时间花在重复的正常流程上，边界值、异常输入、并发这些场景反而容易漏
- **单元测试**：老代码覆盖率很低，开发没时间补；改动时心里没底

## 适用场景

- 适合：需求文档较规范的团队；单元测试覆盖率低、想逐步补齐的项目
- 不值得：需求只在口头沟通的；一次性的脚本
- 前提：有可用的大模型；单元测试能在 CI 里运行

## 工具选型

| 方案                                      | 特点                     | 适用        |
| ----------------------------------------- | ------------------------ | ----------- |
| 大模型 API + 用例模板                     | 生成测试点和用例，可定制 | ✅ 方案采用 |
| AI 编程 Agent（Claude Code、Copilot）     | 补单元测试并自己跑通     | ✅ 方案采用 |
| 测试平台自带 AI（如 Testin、MeterSphere） | 和用例管理集成           | 国内常用    |
| Diffblue Cover                            | Java 单元测试自动生成    | 外企 Java   |

用例生成和单元测试生成分开做：前者输出给测试人员评审，后者必须能运行、能通过。

## 怎么做

**功能测试用例**

- 需求文档 + 用例模板（编号、前置条件、步骤、预期结果、优先级）交给大模型
- 要求按测试设计方法生成：等价类、边界值、异常输入、权限、并发、兼容性
- 测试人员评审：删掉不合理的、补充业务相关的，导入测试管理平台
- 需求变更时，把变更部分交给 AI，标出受影响的用例

**单元测试**

- 每周从覆盖率报告里挑出覆盖率最低、改动最频繁的文件
- AI 编程 Agent 为这些文件补单元测试，必须运行通过、覆盖率确实提升才提 PR
- 只补测试，不改业务代码；发现疑似 bug 时在 PR 里说明，不自行修改

## 关键代码

示例代码（简化），没有在生产环境运行：

```python
PROMPT = """你是资深测试工程师。根据需求生成测试用例，输出 JSON 数组，
字段：id, title, precondition, steps, expected, priority(P0-P2), method。
必须覆盖：正常流程、等价类、边界值、异常输入、权限、并发。
不确定的业务规则写进 questions 字段，不要猜。
需求：
{spec}"""

cases = llm.complete(PROMPT.format(spec=read("PRD-1024.md")), response_format="json")
testhub.import_draft(cases, reviewer="qa-lead")  # 草稿状态，评审后才生效
```

## 效果指标

| 指标               | 做之前             | 预期效果（估算）    |
| ------------------ | ------------------ | ------------------- |
| 写用例时间         | 每个需求半天到一天 | 减半（评审 + 补充） |
| 边界、异常场景遗漏 | 常见               | 按方法逐项覆盖      |
| 单元测试覆盖率     | 低，长期不变       | 每周稳定提升        |

测试人员从「写用例」转为「评审和补充业务场景」；老代码的覆盖率持续提升，改动更有底气。

## 常见坑

- **AI 编造业务规则**：需求没写的规则它会猜。要求不确定的写进问题清单，由人确认。
- **用例数量多但价值低**：生成大量重复用例。限定优先级和数量，评审时合并。
- **单元测试只为凑覆盖率**：断言写得很弱（只检查不报错）。审查时看断言，要求验证具体结果。
- **测试把现有 bug 固化了**：按当前行为写断言，bug 被当成预期。发现可疑行为时标注，由开发确认。

## AI 视角

**🤖 AI 是核心**

- **AI 能做什么**：按测试设计方法系统地列出场景，比人更不容易漏边界和异常；为老代码批量补单元测试
- **不该交给 AI**：业务规则的判断、用例的最终评审、测试是否通过的标准
- **怎么落地**：AI 起草，人评审；单元测试必须能运行通过才提交

## 面试怎么讲

30 秒讲法（方案思路；没有实际落地，面试时如实说明是设计过的方案）：

> 我会分两部分做。功能测试：把需求文档和用例模板交给大模型，要求按等价类、边界值、异常、权限、并发生成用例，不确定的业务规则列成问题，测试人员评审后导入测试平台。单元测试：每周从覆盖率报告挑出覆盖率低、改动多的文件，让 AI Agent 补测试，必须跑通、覆盖率确实提升才提 PR，只补测试不改业务代码。

常见追问：

**问：常用的测试设计方法有哪些？**

答：等价类划分、边界值分析、判定表、状态迁移、错误推测、场景法。

**问：AI 生成的用例怎么保证质量？**

答：模板约束输出格式；要求覆盖指定方法；人评审；用历史需求和人工用例对比，看多发现和遗漏的场景。

**问：覆盖率越高越好吗？**

答：不是。覆盖率说明代码被执行过，不说明结果被验证过；要看断言质量和关键路径覆盖。

**被问到「能不能用 AI」时：** 这个案例本身就是 AI；AI 起草、人评审、测试必须真的能跑。
