## 问题

「系统稳不稳定」常常靠感觉。业务要上新功能、运维要修稳定性，没有共同的数据，只能靠争论。

## 适用场景

- 适合：有明确可用性承诺（SLA）、或者稳定性和迭代速度经常冲突的团队
- 不值得：内部工具、没有用户量的系统
- 前提：有可靠的请求成功率和延迟指标

## 工具选型

| 方案                       | 特点                            | 适用             |
| -------------------------- | ------------------------------- | ---------------- |
| Sloth                      | 从 SLO 定义生成 Prometheus 规则 | 开源，国内外都有 |
| Pyrra                      | 带界面的 SLO 工具               | 开源             |
| Google Cloud / Datadog SLO | 托管                            | 外企常用         |
| 手写 Prometheus 规则       | 完全可控                        | 规则较复杂       |

选 Sloth：一份简单的 YAML 生成全部记录规则和多窗口燃烧率告警，不用自己推导公式。

## 怎么做

- 把可用性定义成可计算的数字：成功请求数 / 总请求数，目标 99.9%（30 天允许约 43 分钟不可用）
- 用 Sloth 从一份 SLO 定义自动生成 Prometheus 记录规则和多窗口燃烧率告警（1 小时烧掉 2% 预算就告警），比固定阈值告警误报少
- Grafana 看板显示本月剩余预算；预算用完就暂停高风险发布
- 周报里加一行 SLO 达成情况

## 实施步骤

| 步骤 | 做什么                                    | 怎么验证                              |
| ---- | ----------------------------------------- | ------------------------------------- |
| 1    | 和业务方确定 SLI 和 SLO（如 99.9%/30 天） | 有书面的 SLO 定义                     |
| 2    | 写 Sloth 定义，生成 PrometheusRule        | Prometheus 里出现 slo: 开头的记录规则 |
| 3    | 导入 SLO 看板                             | 能看到剩余错误预算                    |
| 4    | 配置燃烧率告警                            | 模拟错误时告警按速度分级触发          |
| 5    | 定规则：预算用完暂停高风险发布            | 规则写进发布流程                      |

## 关键代码

示例代码（简化），没有在生产环境运行：

```yaml
slos:
  - name: requests-availability
    objective: 99.9
    sli:
      events:
        error_query: sum(rate(traefik_service_requests_total{code=~"5.."}[{{.window}}]))
        total_query: sum(rate(traefik_service_requests_total[{{.window}}]))
```

## 效果指标

| 指标       | 做之前         | 预期效果（估算）   |
| ---------- | -------------- | ------------------ |
| 可靠性讨论 | 凭感觉争论     | 用剩余错误预算说话 |
| 告警误报   | 固定阈值告警多 | 燃烧率告警更准     |
| SLO 达成   | 没人统计       | 每月可见           |

让「可靠性」变成和业务方都看得懂的数字。本站「平台实况」已经展示 7 天可用率，是这个方案的简化版。

## 常见坑

- **SLO 定得太高**：直接定 99.99%，预算几分钟就用完。先按历史数据定一个能达成的值，再逐步提高。
- **只看服务端指标**：用户侧问题（前端、网络）看不到。结合拨测数据。
- **预算用完没有后果**：规则没人执行。提前和业务约定预算用完的处理方式。

## AI 视角

**⚙️ 规则就够**

- **AI 能做什么**：帮忙解释 SLO 报表、起草和业务方沟通的说明
- **不该交给 AI**：SLO 的计算和燃烧率告警是数学，必须确定
- **怎么落地**：保持规则；月度 SLO 报告可以让 AI 写解读

## 面试怎么讲

30 秒讲法（方案思路；没有实际落地，面试时如实说明是设计过的方案）：

> 我会先和业务方定 SLO，比如核心接口 30 天 99.9% 成功率，也就是每月约 43 分钟的错误预算。用 Sloth 从一份定义生成 Prometheus 规则和多窗口燃烧率告警，Grafana 看板显示剩余预算；预算快用完时暂停高风险发布，优先修稳定性。本站平台实况的 7 天可用率是这个思路的简化版。

常见追问：

**问：SLI、SLO、SLA 的区别？**

答：SLI 是指标（成功率），SLO 是内部目标（99.9%），SLA 是对客户的承诺并带赔偿，通常比 SLO 宽松。

**问：什么是燃烧率告警？**

答：预算消耗速度的倍数。比如 1 小时消耗了月预算的 2% 就紧急告警，6 小时消耗 5% 就一般告警，兼顾灵敏和误报。

**问：99.9% 每月允许多少不可用？**

答：30 天约 43 分钟；99.99% 约 4.3 分钟。

**被问到「能不能用 AI」时：** SLO 是数学计算，不需要 AI；AI 最多帮我把报表解释给业务方听。
