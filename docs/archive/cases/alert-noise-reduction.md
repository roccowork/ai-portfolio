## 问题

数据库一慢，依赖它的十几个服务同时报接口超时、错误率升高、健康检查失败，一分钟内群里刷出几十条告警。值班人员要花时间分辨哪条是源头，真正重要的告警反而被淹没；长期刷屏还会让大家对告警麻木。

## 适用场景

- 适合：服务多、依赖关系复杂、经常出现告警风暴的团队
- 不值得：服务少、告警一天几条的环境，用 Alertmanager 的分组就够了
- 前提：告警带有服务、实例等标签；最好有服务依赖关系（来自链路追踪或 CMDB）

## 工具选型

| 方案                                   | 特点                     | 适用        |
| -------------------------------------- | ------------------------ | ----------- |
| Alertmanager group_by + inhibit_rules  | 规则分组、抑制，确定可控 | ✅ 第一层   |
| 自写聚合服务：时间 + 拓扑 + 文本相似度 | 跨服务合并，标出源头     | ✅ 方案采用 |
| PagerDuty AIOps、BigPanda              | 托管的事件关联           | 外企常用    |
| 夜莺（Nightingale）、睿象云            | 国产告警平台，带收敛功能 | 国内常用    |

先把 Alertmanager 自带的分组和抑制用好，能解决一半问题；剩下的跨服务关联再用聚合服务。

## 怎么做

**第一层：规则降噪**

- `group_by: [alertname, service]`，同一服务同类告警合并成一条消息
- 抑制规则：节点宕机时，抑制该节点上所有 Pod 的告警；数据库宕机时，抑制依赖它的服务的「连接失败」告警

**第二层：智能聚合**

- 告警进入聚合服务后，和最近 10 分钟内未关闭的事件比较，满足以下条件就并入同一个事件：
  - **拓扑相关**：两个服务在依赖图上相邻（来自链路追踪或 CMDB）
  - **文本相似**：告警描述转成向量后，相似度超过阈值（能识别「timeout」和「超时」是一类）
- 事件里按依赖关系找出最上游的告警，标为「可能的源头」
- 一个事件只通知一次，后续合并进来的告警只更新事件，不再单独推送

## 关键代码

示例代码（简化），没有在生产环境运行。Alertmanager 抑制规则：

```yaml
inhibit_rules:
  - source_matchers: [alertname="NodeDown"]
    target_matchers: [severity=~"warning|critical"]
    equal: [node] # 节点宕机时，抑制该节点上的其他告警
```

聚合服务的合并判断：

```python
def find_incident(alert, open_incidents):
    vec = embed(alert.summary)
    for inc in open_incidents:  # 最近 10 分钟未关闭的事件
        near = any(topology.adjacent(alert.service, s) for s in inc.services)
        similar = max(cosine(vec, v) for v in inc.vectors) > 0.85
        if near or similar:
            return inc
    return None
```

## 常见坑

- **误合并**：两个无关的故障碰巧同时发生被合并。拓扑和相似度同时参考，事件里列出所有告警，人可以手动拆分。
- **抑制过度**：源头告警恢复了，被抑制的告警还在却看不到。抑制只在源头告警存在时生效（Alertmanager 默认如此），并定期检查。
- **依赖图过时**：新服务没加进去。依赖图从链路追踪自动生成，而不是手工维护。
- **只做降噪不治本**：告警本身设计得不好（阈值太低、没意义的告警）。定期清理从来没人处理的告警。

## AI 视角

**🤖 AI 是核心**

- **AI 能做什么**：用文本向量判断告警描述是否说的是同一件事，结合拓扑把分散的告警归成一个事件；还可以用大模型给事件写一句人能读懂的摘要
- **不该交给 AI**：抑制规则这类确定的逻辑用规则写；是否通知、通知谁按规则
- **怎么落地**：规则降噪打底，AI 做跨服务、跨措辞的关联；聚合后的事件再交给根因分析

## 面试怎么讲

30 秒讲法（方案思路；没有实际落地，面试时如实说明是设计过的方案）：

> 我会分两层降噪。第一层用好 Alertmanager 的 group_by 和抑制规则，比如节点宕机时抑制它上面所有 Pod 的告警。第二层写一个聚合服务，新告警和最近 10 分钟的事件比较，在服务依赖图上相邻、或者描述的文本向量相似，就并入同一个事件，并按依赖关系标出最上游的源头告警，一个事件只通知一次。先统计降噪前的告警量作为基线，上线后对比效果。

常见追问：

**问：group_by、inhibit、silence 有什么区别？**

答：group_by 把多条告警合成一条消息；inhibit 是某个告警存在时自动屏蔽另一些告警；silence 是人手动在一段时间内屏蔽告警，比如维护期间。

**问：服务依赖图从哪来？**

答：最好从链路追踪自动生成（调用关系），其次从 CMDB 或服务注册中心；手工维护很快就过时。

**问：为什么要用文本相似度？**

答：不同服务对同一个问题的描述不一样，比如「connection timeout」「连接超时」「upstream timed out」，规则很难写全，向量相似度能识别出它们是一类。

**被问到「能不能用 AI」时：** 规则降噪打底，AI 负责规则写不全的跨服务、跨措辞关联。
