## 问题

告警只说「接口 P99 延迟超过 1 秒」，值班人员要自己打开 Grafana 看指标、去 Loki 搜日志、查 K8s 事件、翻最近谁发布了什么，十几分钟后才有方向。经验少的新人更慢，半夜更容易漏看关键线索。

## 适用场景

- 适合：服务多、告警多、值班人员经验参差不齐的团队
- 不值得：只有几个服务、告警很少的环境
- 前提：指标、日志、发布记录都已集中采集；有可用的大模型（云端或私有部署）

## 工具选型

| 方案                              | 特点                    | 适用        |
| --------------------------------- | ----------------------- | ----------- |
| 自写服务：收集上下文 + 大模型 API | 可控，可接私有模型      | ✅ 方案采用 |
| Datadog Bits AI、PagerDuty AIOps  | 和自家监控深度集成      | 外企常用    |
| 阿里云 ARMS、腾讯云智能运维       | 云上托管                | 国内云上    |
| k8sgpt                            | 开源，专注 K8s 问题诊断 | K8s 环境    |

自写服务的关键不在模型，而在「收集哪些上下文」：按告警类型决定查哪些指标和日志，喂给模型的是整理好的证据，不是原始数据。

## 怎么做

- Alertmanager 把告警同时发给人和分析服务（webhook，`continue: true`），分析不影响原有通知
- 分析服务按告警的标签（服务名、命名空间、实例）收集上下文：
  - 告警指标前后 1 小时的曲线摘要（最大值、突变时间点）
  - 同一服务最近 15 分钟的错误日志，按模板去重后取前 20 种
  - K8s 事件：重启、OOMKilled、调度失败
  - 最近 2 小时的发布和配置变更
  - 相关的 runbook 片段
- 交给大模型，要求输出固定格式：最可能的 1～3 个原因、每个原因对应的证据、建议的下一步排查或处置
- 结果作为告警的回复发到群里；值班人员点「对 / 不对」，反馈用于改进提示词和收集的上下文

## 实施步骤

| 步骤 | 做什么                                   | 怎么验证                     |
| ---- | ---------------------------------------- | ---------------------------- |
| 1    | 按告警类型整理「该看哪些数据」           | 每类告警有一份上下文清单     |
| 2    | 写上下文收集：指标、日志、事件、发布记录 | 手动触发能拿到完整上下文     |
| 3    | 设计提示词和输出格式，要求附证据         | 输出结构固定，每个结论有证据 |
| 4    | 用过去 3 个月的故障回放                  | 和复盘结论一致的比例         |
| 5    | 上线，结果发到告警群，收集「对 / 不对」  | 每周统计准确率               |

## 关键代码

示例代码（简化），没有在生产环境运行：

```python
def investigate(alert):
    svc, ns = alert.labels["service"], alert.labels["namespace"]
    ctx = {
        "alert": alert.summary,
        "metrics": summarize(prom.range(alert.expr, hours=1)),
        "errors": top_templates(loki.query(f'{{app="{svc}"}} |= "error"', since="15m"), 20),
        "k8s_events": k8s.events(ns, svc, since="30m"),
        "changes": deploys.recent(svc, hours=2),
        "runbook": runbook.search(alert.name),
    }
    prompt = RCA_PROMPT.format(**ctx)  # 要求：最多 3 个原因，每个原因引用具体证据
    return llm.complete(prompt, response_format=RCA_SCHEMA)
```

## 常见坑

- **AI 编造原因**：上下文里没有证据也给出结论。要求每个原因必须引用具体的日志行或指标值，没有证据的不展示。
- **上下文太多超出限制**：把原始日志全部塞进去。先按模板去重、只取错误日志、指标只给摘要。
- **敏感信息外传**：日志里有手机号、密钥。发送前脱敏，或用私有部署的模型。
- **告警风暴时调用量暴增**：几百条告警同时触发。先做告警聚合，一个故障只分析一次。
- **大家开始不看监控只看 AI**：AI 结论错了没人发现。结论只是方向，处置前要人确认证据。

## AI 视角

**🤖 AI 是核心**

- **AI 能做什么**：把分散在指标、日志、事件、发布记录里的线索串起来，用人能读懂的话给出可能原因和下一步
- **不该交给 AI**：最终判断和处置决定；涉及数据的操作
- **怎么落地**：程序负责按规则收集上下文，大模型负责分析和总结，人负责确认和处置

## 面试怎么讲

30 秒讲法（方案思路；没有实际落地，面试时如实说明是设计过的方案）：

> 我会让 Alertmanager 把告警同时发给一个分析服务。它按告警的服务名收集上下文：指标曲线摘要、去重后的错误日志、K8s 事件、最近 2 小时的发布，再加上对应的 runbook，交给大模型，要求输出最多 3 个可能原因，每个都附上具体证据。结果发到告警群，值班人员反馈对不对，用来持续改进。上线前用过去 3 个月的故障回放评估准确率。

常见追问：

**问：效果好坏主要取决于什么？**

答：主要取决于上下文收集得准不准。模型只能分析你给它的数据，所以要按告警类型整理好该查哪些指标和日志。

**问：怎么防止 AI 胡说？**

答：要求结论必须引用证据；证据由程序收集，可以核对；没有证据的结论不展示；用历史故障回放评估准确率。

**问：和告警降噪是什么关系？**

答：先降噪，把一个故障引起的多条告警合并成一条，再对这一条做根因分析，避免重复分析和调用量暴增。

**被问到「能不能用 AI」时：** 这个案例本身就是 AI；关键是程序收集证据、AI 分析、人确认。
