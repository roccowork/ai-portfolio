## 问题

开发直接连生产库改数据：一条忘了 WHERE 的 UPDATE 就能改坏整张表；DBA 每天被找去帮忙执行 SQL，也没有记录。

## 适用场景

- 适合：开发人数多、经常要改生产数据的公司；有等保或审计要求的
- 不值得：只有一两个人、DBA 就是开发本人的小团队
- 前提：能收回开发直连生产库的权限

## 工具选型

| 方案                         | 特点                          | 适用       |
| ---------------------------- | ----------------------------- | ---------- |
| Archery                      | 国产开源，审核 + 查询 + 工单  | 国内最常用 |
| Yearning                     | 国产开源，界面简洁            | 国内常用   |
| Bytebase                     | 开源，支持多种数据库和 GitOps | 国内外都有 |
| Liquibase / Flyway + PR 审核 | 变更走代码评审                | 外企常用   |

选 Archery：审核规则、审批流、执行、回滚语句生成和查询脱敏一站式，国内资料多。

## 怎么做

- 开发不再拿生产库账号，所有变更通过 SQL 审核平台（国内常用 Archery、Yearning）提交
- 提交时自动审核：禁止不带 WHERE 的 UPDATE/DELETE、预估影响行数、大表 DDL 提示走在线变更工具
- 按风险分级审批：查询直接执行，数据修改要主管审批，DDL 要 DBA 审批
- 执行前自动备份受影响的数据并生成回滚语句；全部操作留痕

## 实施步骤

| 步骤 | 做什么                                   | 怎么验证                        |
| ---- | ---------------------------------------- | ------------------------------- |
| 1    | 部署 Archery，接入生产库（专用账号）     | 能在平台上执行只读查询          |
| 2    | 配置审核规则：禁止无 WHERE、提示大表 DDL | 提交测试 SQL 时被正确拦截       |
| 3    | 配置审批流：数据修改要主管、DDL 要 DBA   | 工单按金额/类型流转到对应审批人 |
| 4    | 收回开发的生产库直连权限                 | 开发只能通过平台操作            |
| 5    | 开启执行前备份和回滚语句                 | 执行记录里有回滚 SQL            |

## 关键代码

示例代码（简化），没有在生产环境运行：

```yaml
# 审核规则示意（各平台配置方式不同）
rules:
  - { name: dml_without_where, level: error } # 不带 WHERE 的 UPDATE / DELETE 直接拒绝
  - { name: affected_rows_over, level: warning, value: 10000 }
  - { name: ddl_on_big_table, level: warning, value: 1000000 } # 大表改结构提示用 gh-ost
```

## 效果指标

| 指标       | 做之前                    | 预期效果（估算）             |
| ---------- | ------------------------- | ---------------------------- |
| 误操作风险 | 一条错误 SQL 可能改坏整表 | 提交时自动拦截               |
| DBA 工作量 | 帮人执行 SQL              | 只审核高风险变更             |
| 审计       | 没有记录                  | 每条变更有人、有时间、有审批 |

生产数据变更可控、可回滚、可追溯；DBA 从「帮人执行」变成「审核把关」。

## 常见坑

- **预估影响行数和实际差很多**：EXPLAIN 估算不准。高风险语句先在从库或测试库 count 一遍。
- **平台账号权限过大**：平台用 root 连接。给平台的账号只授必要权限，按库区分。
- **紧急情况平台不可用**：平台本身挂了。保留一条有审批和记录的应急通道（堡垒机）。

## AI 视角

**✨ AI 能增强**

- **AI 能做什么**：对复杂 SQL 给出优化建议和风险说明
- **不该交给 AI**：拦截规则必须确定
- **怎么落地**：审核规则先过，AI 补充优化建议

## 面试怎么讲

30 秒讲法（方案思路；没有实际落地，面试时如实说明是设计过的方案）：

> 我会部署 Archery 这类 SQL 审核平台，收回开发直连生产库的权限。提交 SQL 时自动审核：不带 WHERE 的 UPDATE、DELETE 直接拒绝，估算影响行数，大表 DDL 提示用在线变更工具；按风险分级审批，执行前自动备份并生成回滚语句，所有操作留痕。

常见追问：

**问：为什么不让开发直接连生产库？**

答：误操作没人拦、没有审计、权限无法回收；通过平台可以审核、审批、备份和记录。

**问：如何快速恢复误删的数据？**

答：有执行前备份就直接用回滚语句；没有的话用 binlog 闪回（如 my2sql）或从全量备份 + binlog 恢复到误操作前。

**问：大表加字段会锁表吗？**

答：MySQL 8.0 很多加列操作支持 INSTANT，不锁表；不支持的用 gh-ost 在线变更。

**被问到「能不能用 AI」时：** 审核规则是硬性的，AI 补充优化建议。
