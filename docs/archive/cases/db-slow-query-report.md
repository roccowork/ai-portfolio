## 问题

数据库越来越慢，开发说「SQL 没问题」，DBA 说「SQL 写得烂」，没有数据就只能互相推。

## 适用场景

- 适合：数据库变慢、开发和 DBA 之间需要数据说话的团队
- 不值得：访问量很小的数据库
- 前提：能开启慢查询日志，日志能被分析工具读取

## 工具选型

| 方案                        | 特点                         | 适用         |
| --------------------------- | ---------------------------- | ------------ |
| pt-query-digest             | Percona 工具，聚合分析       | 国内外都常用 |
| Performance Schema / sys 库 | MySQL 自带统计               | 不用读日志   |
| PMM                         | Percona 监控平台，带查询分析 | 开源         |
| 云数据库 SQL 洞察           | 托管                         | 云上         |

选 pt-query-digest：把同结构 SQL 聚合，按总耗时排序，直接得出最该优化的几条。

## 怎么做

- 开启慢查询日志：超过 1 秒的 SQL 记录下来，日志按天切割
- 每天凌晨用 Percona 的 pt-query-digest 分析前一天的日志：相同结构的 SQL 合并，按总耗时排序
- 前 10 名附上执行次数、平均耗时、扫描行数和 EXPLAIN 结果，没走索引的标出来
- 报告发到开发群；连续一周上榜的 SQL 建任务跟进

## 实施步骤

| 步骤 | 做什么                       | 怎么验证           |
| ---- | ---------------------------- | ------------------ |
| 1    | 开启慢查询日志，阈值 1 秒    | 日志里有记录       |
| 2    | 日志按天切割                 | 每天一个文件       |
| 3    | 每天凌晨运行 pt-query-digest | 生成 Top 10 报告   |
| 4    | 附上 EXPLAIN 和索引建议      | 能看出哪些没走索引 |
| 5    | 报告发到开发群并跟踪         | 连续上榜的建任务   |

## 关键代码

示例代码（简化），没有在生产环境运行：

```bash
pt-query-digest --since 24h --limit 10 --order-by Query_time:sum \
  /var/log/mysql/slow.log > /tmp/slow-$(date +%F).txt
# 实验 04 的巡检脚本里已有 MySQL 检查项，这里只多一份每日 SQL 分析
```

## 效果指标

| 指标       | 做之前       | 预期效果（估算）      |
| ---------- | ------------ | --------------------- |
| 优化目标   | 凭感觉       | 按总耗时排序的 Top 10 |
| 优化效果   | 说不清       | 第二天报告里对比      |
| 慢查询发现 | 用户投诉变慢 | 每天主动报告          |

优化有了明确目标和效果对比：优化后第二天的报告里就能看到这条 SQL 消失。

## 常见坑

- **阈值太低日志巨大**：long_query_time 设成 0。设 1 秒；需要全量分析时短时间开启。
- **只看单次耗时**：忽略执行次数多的中等慢查询。按总耗时（次数 × 平均）排序。
- **慢查询日志里有敏感数据**：SQL 含手机号等参数。报告里只展示脱敏后的 SQL 指纹。

## AI 视角

**✨ AI 能增强**

- **AI 能做什么**：针对慢 SQL 给出改写和索引建议
- **不该交给 AI**：Top 10 统计必须确定
- **怎么落地**：报告里每条慢 SQL 附 AI 优化建议

## 面试怎么讲

30 秒讲法（方案思路；没有实际落地，面试时如实说明是设计过的方案）：

> 我会开启 MySQL 慢查询日志，阈值 1 秒、按天切割，每天凌晨用 pt-query-digest 分析前一天的日志：相同结构的 SQL 合并，按总耗时排序取前 10，附上执行次数、平均耗时、扫描行数和 EXPLAIN 结果，没走索引的标出来，发到开发群。优化后第二天的报告就能看到效果。

常见追问：

**问：怎么看 EXPLAIN？**

答：重点看 type（ALL 是全表扫描）、key（用了哪个索引）、rows（估计扫描行数）、Extra（Using filesort、Using temporary 需要关注）。

**问：索引失效的常见原因？**

答：对索引列用函数或计算、隐式类型转换、like 以 % 开头、联合索引不满足最左前缀。

**问：为什么按总耗时排序？**

答：一条 0.5 秒但每天执行 10 万次的 SQL，比一条 10 秒每天 1 次的影响大得多。

**被问到「能不能用 AI」时：** 慢查询统计是规则，AI 给出索引和改写建议，开发直接参考。
