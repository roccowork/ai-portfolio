## 问题

滚动更新只能保证「新 Pod 就绪」，不能保证「新版本没 bug」。一个影响全部用户的坏版本，发现时往往已经造成损失。

## 适用场景

- 适合：用户量大、一次故障影响面广的线上服务（电商、支付、SaaS）
- 不值得：内部工具、访问量很小的服务——10% 流量里样本太少，指标判断不出好坏
- 前提：有可靠的错误率、延迟指标；应用支持多版本同时运行（数据库变更向前兼容）

## 工具选型

| 方案                      | 特点                      | 适用           |
| ------------------------- | ------------------------- | -------------- |
| Argo Rollouts             | K8s 原生，和 Argo CD 配合 | 国内外都常用   |
| Flagger                   | 配合 Flux 或服务网格      | 外企云原生团队 |
| Istio / 服务网格          | 按请求头、比例精细切流量  | 大规模微服务   |
| Nginx Ingress canary 注解 | 最简单，按比例或请求头    | 国内常用       |

选 Argo Rollouts：和现有 Argo CD 无缝衔接，分析步骤直接查 Prometheus，不需要引入服务网格。

## 怎么做

- 用 Argo Rollouts 的 Rollout 替换 Deployment，发布分步：10% → 观察 5 分钟 → 50% → 观察 → 100%
- 每一步用 AnalysisTemplate 查 Prometheus：5xx 比例 < 1%、p95 < 500ms，任何一步不达标自动回退到旧版本
- 流量按比例切分由 Traefik 的加权服务实现，不需要服务网格
- 和现有 GitOps 流程兼容：CI 照常改镜像标签，Argo CD 同步 Rollout

## 实施步骤

| 步骤 | 做什么                                   | 怎么验证                                 |
| ---- | ---------------------------------------- | ---------------------------------------- |
| 1    | 安装 Argo Rollouts 控制器和 kubectl 插件 | `kubectl argo rollouts version` 正常     |
| 2    | 把 Deployment 改成 Rollout，定义分步策略 | 发布时 `get rollout` 显示当前步骤        |
| 3    | 写 AnalysisTemplate：5xx 比例、p95       | 手动运行分析能拿到 Prometheus 数据       |
| 4    | 配置流量切分（Traefik 加权服务）         | 10% 步骤时用脚本统计约 1/10 请求到新版本 |
| 5    | 演练：发一个返回 500 的坏版本            | 分析失败，自动回退到旧版本               |

## 关键代码

示例代码（简化），没有在生产环境运行：

```yaml
strategy:
  canary:
    steps:
      - setWeight: 10
      - analysis: { templates: [{ templateName: error-rate }] }
      - setWeight: 50
      - pause: { duration: 5m }
      - setWeight: 100
```

## 效果指标

| 指标           | 做之前                   | 预期效果（估算）    |
| -------------- | ------------------------ | ------------------- |
| 坏版本影响范围 | 100% 用户                | 约 10% 用户、几分钟 |
| 发现坏版本     | 用户反馈或告警后人工回滚 | 分析失败自动回退    |
| 发布值守       | 需要人盯着               | 无人值守            |

坏版本最多影响 10% 的请求、几分钟，并且不需要人值守。本站单副本静态站点用不上，所以只做方案。

## 常见坑

- **10% 流量里错误率波动大，误判回退**：流量小时样本不足，几个错误就超过阈值。分析加最小请求数条件，或延长观察时间。
- **新旧版本同时运行时数据库报错**：新版本改了表结构，旧版本不兼容。数据库变更分两步：先加字段（兼容），全量后再删旧字段。
- **回退后 Argo CD 显示 Degraded**：Rollout 处于中止状态。修复后推新版本，或手动 `promote`/`retry`。

## AI 视角

**✨ AI 能增强**

- **AI 能做什么**：分析金丝雀期间新旧版本的日志和链路差异，解释为什么指标变差
- **不该交给 AI**：放量和回退的判断要基于明确的指标阈值，不能交给模型「感觉」
- **怎么落地**：回退发生后自动收集两个版本的错误日志交给 AI 做对比摘要

## 面试怎么讲

30 秒讲法（方案思路；没有实际落地，面试时如实说明是设计过的方案）：

> 如果要做金丝雀发布，我会用 Argo Rollouts 替换 Deployment，发布分成 10%、50%、100% 几步，每步用 AnalysisTemplate 查 Prometheus 的 5xx 比例和 p95，任何一步不达标自动回退。流量切分用 Traefik 的加权服务，不需要服务网格。要注意流量小时样本不足会误判，以及新旧版本同时运行要求数据库变更向前兼容。

常见追问：

**问：金丝雀和蓝绿发布有什么区别？**

答：蓝绿是两套完整环境一次性切换，回滚快但资源翻倍；金丝雀逐步放量，资源省、影响面小，但新旧版本要能共存。

**问：怎么判断新版本是好是坏？**

答：对比新版本和旧版本的错误率、延迟，最好还有业务指标（下单成功率）；只看新版本的绝对值容易受整体流量波动影响。

**问：数据库变更怎么配合灰度？**

答：扩展-收缩模式：先只做向前兼容的变更（加字段、加表），新旧版本都能跑；全量后再清理旧字段。

**被问到「能不能用 AI」时：** 放量回退靠指标阈值，AI 用来在回退后快速解释新版本哪里出了问题。
